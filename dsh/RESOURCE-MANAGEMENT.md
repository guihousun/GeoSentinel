# 多用户资源与队列管理

## 默认策略

| 层级 | 每账号同时运行 | 全平台同时运行 | 满额处理 |
| --- | --- | --- | --- |
| 研究对话 | 2 | 10 | 自动排队 |
| Docker 计算 | 2 | 10 | 自动排队 |
| 提问频率 | 每分钟 20 次 | 不按在线人数限制 | HTTP 429 |

研究队列只控制请求派发与名额，不替代 AgentTeams。规划、成员协作、原生 Todo 和方案确认仍由现有架构负责。

- 按到达顺序选择有可用名额的账号；某账号达到上限时，其他账号不必陪同等待。
- 同一对话的请求依次派发，不同时启动两个根智能体回合。不同对话可并行。
- 等待任务最多每账号 20 项、全平台 200 项，防止无限堆积；队列满时仍会拒绝新请求。这是等待容量，不是运行并发。
- 等待列表只向当前对话所有者开放。输入栏上方显示等待数量及可展开摘要；停止会同时取消本对话未派发请求与计算调用。
- 方案批准可以排队，但绑定批准时的 `teamId` 和 `revision`，执行前再次核验。修改过的方案不能用旧批准执行。
- 公共监测独立运行，不占研究队列名额，它的资源不计入这两个并发上限。

## 部署配置

在 `dsh/.env` 或 `GEO_ENV_FILE` 指定的配置中设置，重启服务生效：

```dotenv
GEO_RESEARCH_CONCURRENCY=10
GEO_USER_RESEARCH_CONCURRENCY=2
GEO_DOCKER_CONCURRENCY=10
GEO_USER_DOCKER_CONCURRENCY=2
GEO_DOCKER_MEMORY_MIB=3072
GEO_MIN_FREE_DISK_MIB=1024
```

每容器默认限 1 CPU、3 GiB 内存、128 个进程和 30 分钟执行时间。`GEO_DOCKER_MEMORY_MIB` 使用整数 MiB：3072 是 3 GiB，4096 是 4 GiB，不填写 `4g`。这是每容器上限，不是启动时固定预占全部内存；交换空间还受 Docker/宿主配置影响。

10 个容器不表示机器一定能承载该负载：3 GiB 配置的内存上限合计 30 GiB，4 GiB 配置则为 40 GiB，还要加宿主系统、Docker、DSH 与监测开销。默认采用 3 GiB；确有大栅格需求且内存充足时才改 4 GiB，或同时调低 `GEO_DOCKER_CONCURRENCY`。并发数不是 GPU、Token 或 API 费用预算。

### 已有部署升级

1. 等待或停止当前研究，备份完整 DSH home 和外置平台数据目录；备份要求见 [迁移教程](../docs/migration-to-dsh.md)。
2. 在代码目录运行 `git status -sb`；有本地修改时先妥善保存，不要强制覆盖。然后执行 `git pull --ff-only origin main`。
3. 进入 `dsh/` 执行 `pnpm install --frozen-lockfile`。保留既有 `.env`、账号库和工作区，不复制 `.env.example` 覆盖它们。
4. 在实际使用的 `.env` 中加入上述并发和内存参数。若要 4 GiB，仅将 `GEO_DOCKER_MEMORY_MIB` 改为 `4096`，并核对 Docker Desktop 的总内存分配。
5. 运行 `node scripts/check-env.mjs`；确认预期数据目录后，以原来的 `GEO_DSH_HOME`、`GEO_DATA_DIR`、端口和启动命令启动服务。不要为了升级重新初始化管理员。
6. 新表和删除时间字段由程序增量迁移。新限制对重启后的新作业生效，不会修改已经运行的容器。本次资源参数变更不需要重建 GIS 镜像。
7. 登录后在账号/管理中心检查用量入口，提交小任务核实问答、排队、取消和文件下载正常。旧版运行状态不具备队列记录，应在升级前先停止。

队列等待不占容器运行超时；等待调用仍受上层智能体取消与工具生命周期约束。浏览器关闭不会自动取消研究。

## 持久化与重启

`platform.sqlite` 新增运行队列、限流窗口和用量表。服务在此数据库记录本机进程占用，避免同一数据目录从不同端口重复启动。只能由同一主机上的一个调度服务使用；PID 存活判断保守处理权限错误和 PID 重用，不提供分布式锁。

1. 未派发的研究问题和已确认方案保留为等待状态，服务恢复后按名额继续派发。
2. 已派发研究标记中断，恢复团队时停止旧执行，不自动重放问题或 Python 脚本。已有输出保留给用户检查。
3. 旧进程内正在执行或等待的 Docker 调用标记中断。模型调用栈无法跨进程恢复，不能将容器启动冒充为对话恢复，需重新提交研究。
4. 启动时按平台目录哈希标签清理当前平台遗留容器，不触碰其他平台容器。清理失败则暂缓相关计算派发并保留恢复标记。
5. 派发时重查用户停用、项目归档/删除、对话删除和方案版本；失效请求取消或失败，不执行。

第一次从旧版本升级应先停止所有运行任务，再备份并重启；此前没有队列表记录的任务不能追溯性恢复。数据库迁移为增量建表/加列，已有账号、对话和文件保留。

## 用量与存储

账号入口查看本人用量，管理中心查看平台汇总。API：`GET /geo/api/account/usage`、管理员专用的 `GET /geo/api/admin/usage`。

- 接收问题次数、成功写入项目输入的累计字节数。
- 研究/计算任务排队、运行、取消、失败和中断次数。
- 已结束计算作业的墙钟运行时长和成功输出字节数，不是 CPU 实际使用时长。
- 当前用户工作区磁盘占用，不含公共监测、全局作业日志与 DSH 独立会话存储。
- 调度完成只表示运行流程结束，不等于科学结果验收通过。未实现 Token 计费、API 费用或用户总磁盘硬配额。

上传单文件 16 MiB、项目输入 512 MiB。同项目上传与公共事件导入经过同一串行配额检查，禁止覆盖同名文件。计算输出每作业限制 256 MiB、2000 个目录项，每秒检查，超出后终止；仍可能短暂超量，不是内核硬配额。

磁盘默认预留 1 GiB：上传和新计算前检查，计算开始前还预留作业输出预算，运行中持续检查。不自动删除正常资料腾出空间。高负载或不可信环境还应设置宿主文件系统配额及磁盘监控。

## 结果依赖待办（暂不实施）

以下两项已记录，按用户决定本轮不修改现有 `previous/` 挂载与结果读取机制：

1. **明确依赖后再开放读取**：只向作业开放其明确依赖、已完成并通过检查的前序结果，避免读取并行作业尚未写完的文件。当前 `previous/` 仍挂载本对话的整个输出目录，尚不具备此项保证。
2. **统一结果状态和来源记录**：在现有作业状态与部分来源记录基础上，完善文件级所属作业、完整性、来源和校验结果，并据此决定是否允许下游使用，不能仅凭文件存在。目前尚未实现统一的文件级准入校验。

## 清理流程

只供管理员本机停机维护使用。默认预览，不自动定时删除：

```powershell
cd D:\GeoSentinel-DSH\dsh
# 使用与服务相同的 GEO_ENV_FILE / GEO_DSH_HOME / GEO_DATA_DIR。
# 先停止该平台服务并完成备份。
node scripts/maintenance.mjs --days=30
# 核对返回路径和字节数后才执行：
node scripts/maintenance.mjs --days=30 --apply
```

仅处理超过保留期、已软删除且没有排队/运行任务的项目或对话工作区，以及可对应到这些对话的作业目录。递归删除前校验绝对路径仍在平台根目录内，拒绝符号链接和目录联接。

正常项目、仅归档项目、公共监测、数据库审计与 DSH 会话记录不在清理范围。数据库保留删除/清理时间。此操作不是账号彻底注销或安全擦除。升级前已删除的条目从迁移时开始计算保留期，不会因缺少旧删除时间而立刻清除。

## 验证与边界

`pnpm test` 覆盖并发、跨对话排队、可运行账号优先、重启、取消、权限重验、持久限流、上传竞争、磁盘保护与清理路径隔离。`node scripts/smoke-isolation.mjs` 在隔离工作区验证真实 Docker 并行、第三项等待、取消与输出限制，不调用模型或 GEE。

不承诺跨机容灾、恰好一次外部 API 副作用或全量续跑。派发与落盘之间存在不确定状态时采用中断而非重试，避免重复下载与扣费。
